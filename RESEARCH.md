# Research: making the viewer lighter and faster

This file collects findings on making a Tauri 2 document viewer lighter and faster. It covers start-up time, idle CPU, memory with large files, smoothness and size. The findings come in four tracks: official sources, Tauri GitHub issues, community sources and reference apps. Nothing here has been measured on our app; the "Decision" column says what we do with each finding and why. "Plan" means it is in the ordered plan, "Big move" means it waits for approval, and "Watch" means an open upstream issue we cannot fix from our side. IDs are fixed. A missing number means that row is listed under "Does not apply or rejected at source".

Date: 2026-11-15

Stack the findings were filtered for: Tauri 2.12.0, wry 0.57.1, tao 0.37.2, tauri-utils 2.10.0, WebView2 runtime 157, React 18.3.1, Vite 5.4, pdfjs-dist 4.10 (legacy build), build target chrome89. Platforms: Windows, macOS, Linux, Android.

Effort key: S is under half a day, M is a day or two, L is more.

## Top candidates

These are the findings that change what we do. Rows 1, 2, 7 and 8 were checked against our code and lock file. The others come from the sources and the code audits and still need the baseline to confirm their size.

| # | Finding | Sources | What we do |
|---|---|---|---|
| 1 | A bundled script with `%PDF` in its first 1,024 bytes is served as a PDF and the app stays blank. We are on the affected versions (`tauri-utils` 2.10.0, `infer` 0.22.0) and our code holds that literal. | R2-01 | A build check that fails when any chunk has the marker in its first 1,024 bytes. Safe today only by chunk layout. |
| 2 | The window and the page both paint before the saved theme is known, so a saved theme that differs from the default flashes. | R1-10, R2-06, R2-07, R3-04, R4-01 to R4-04, R4-27 | Apply the last theme before first paint (a small inline script and a stored hint), and set the window colour from it. Hide-until-ready only if frames still show a flash. |
| 3 | No setting throttles a hidden or minimised window on Windows, Linux or Android. | R1-16 (rejected list), R2-23, R3-24 | Stop our own timers, loops and polls when the document or the tab is not on show. |
| 4 | Idle and scroll CPU in webviews comes mostly from animating non-compositor properties and from re-renders caused by unstable references. | R1-35, R2-34, R3-03, R3-13 | MOTION.md rule 1 and its section 5; stable context values and memo boundaries at the measured hot spots. |
| 5 | Binary IPC on Windows is the slowest of the platforms (about 200 ms for 10 MB in one maintainer's test), and `readFile` holds the whole file in memory. | R2-02, R3-01, R3-02 | Never send the same bytes twice (Save a copy re-reads today). Loading by URL with ranges is a big move, listed separately. |
| 6 | pdf.js keeps page data until `cleanup()` runs; one report measured about 80 MB per rendered page. | R3-08, R4-39 | A size budget for the tabs kept alive, and cleanup when a tab goes out of view. |
| 7 | A click on a drag region can lose its mouse-up; the wry half of the fix is in 0.57.2 and we are on 0.57.1. | R2-10, R2-40 | `cargo update -p wry`. |
| 8 | A window event handler that calls a command on every event keeps the main thread busy. | R2-11 | Debounce the title bar's per-resize call. |
| 9 | With a CSP, every script chunk adds a hash to the response header; past 16 KiB macOS shows a blank window. | R2-25 | A build check on the chunk count. |
| 10 | `content-visibility: auto` cut a demo's first render from 232 ms to 30 ms. | R1-34, R3-19 | Already used in four viewers; extend only to lists the baseline shows are slow. |

Decided against, with the reason: WebView2 browser flags (Microsoft advises against them in production: R4-23, R4-24), a different allocator (more memory for less CPU in the one measured test, and a core this small gains nothing), `opt-level = "z"` (not reliably smaller than `"s"`), the React compiler and list-virtualisation libraries (new dependencies; the hot spots are few enough to fix by hand), and the Linux compositing variables as a default (Tauri's own docs warn against it).

## Conflicts between sources

Both sides are stated. None is resolved here.

- **WebView2 browser flags.** Side A: Microsoft says no flags in production, `additionalBrowserArgs` replaces wry's default disables, and the GPU should stay on (R1-17, R1-18, R3-05). Side B: Pake and Seelen UI ship flags (R4-23, R4-24, and R4-25 for the GPU flags); a Microsoft Q&A answer suggests `--disk-cache-size` (R3-09). R4-23 repeats the three `ms*` disables that R1-17 says wry already passes.
- **Background throttling and hidden windows.** Side A: throttling is unsupported on Windows, Linux and Android, so there is nothing to enable, and minimised idle CPU is mostly WebView2's own (R1-16, R2-23, R3-24). Side B: a hidden window still burned about one core because each Tauri event resumes the webview (R3-03); Readest and Seelen turn throttling off (R4-26); manual `TrySuspend` is offered as the route (R1-15).
- **Hiding the window until the first paint.** For: R1-10, R2-07, R2-08, R3-04, R4-01, R4-02, R4-04. Against or with risks: hide then show can add about 200 ms (R3-04); hide, show and maximize caused a jump and flash (R2-06); a hidden window never fires rAF, so a timer race is needed (R4-01); a failed show call leaves the window invisible (R1-10). The show moment also differs: after two rAF (R4-01), at page load (R4-02), after the first React effect (R2-07). Focus differs too: `set_focus()` on show (R4-01, R2-06) against no focus on the cold-start show (R4-27).
- **Allocator choice.** R1-24 (rejected) says alternative allocators can give large gains but raise binary size and compile time. R3-16 (rejected) measured mimalloc at about 16% less renderer CPU but about 25% more private memory. Both reject it for us, for different reasons.
- **Linux compositing and rendering variables.** R1-29, R2-28 and R3-10 say do not ship the variables unconditionally; R2-28 also says set `WEBKIT_DISABLE_COMPOSITING_MODE` in Rust before `tauri::Builder` on affected machines. `LIBGL_ALWAYS_SOFTWARE=1` fixed the blank window in R2-28 but did not help in R3-11, where only `WEBKIT_SKIA_ENABLE_CPU_RENDERING=1` did. `WEBKIT_DISABLE_DMABUF_RENDERER=1` is the fix for R2-29 but did not help in R3-11. R3-20 says `backdrop-filter` breaks when DMABUF is off. R1-31 offers `hardware-acceleration-policy`; R2-30 says Tauri has no such option and points to the compositing variable.
- **Channels against raw responses.** R1-08 (dropped) says Channels are fast and ordered, and R1-09 streams a file through one. R2-18 says a Channel is slower than an `ipc::Response` or custom protocol because the receiver pulls the data. R2-20 measured Channel memory growth.
- **Android Range requests.** R2-16 says wry 0.57.1 fixes the double-applied Range on Android. R4-11 still avoids the Range header and cites tauri#12019 and tauri#3725 as the reason. R2-17 reports further Range problems on Linux. R3-23 says a custom scheme gives no extra gain on Windows, while R4-12 says a custom scheme is only worth it for our own scope or MIME rules.
- **IPC cost numbers on Windows.** R3-01 gives 1.8 s for 150 MB (about 12 ms per 10 MB if linear). R3-02 gives about 200 ms for 10 MB. R2-03 gives about 4 GB RAM for a 600 MB file even with raw `Response`, and R2-02 expects 2 to 3 times the file size in flight.
- **Reading files in chunks.** R2-02 lists chunked `open()` and `FileHandle.read` as an option. R4-40 measured per-chunk open, seek, read, close at 44 MB/s against 281 MB/s for one asset `fetch`.
- **Transparent windows.** R2-08 says `transparent:true` removes the Windows resize bars. R2-26 says it costs about 8 times the GPU power on macOS, and R3-11 says it painted nothing on one Linux setup. R3-04 says macOS `background_color` sits behind the `transparent` feature, while R2-27 says the native background colour is the only mitigation for macOS white gaps.
- **Window shadow and undecorated windows.** R4-28 calls `set_shadow(true)` after build. R2-12 says shadow makes `set_min_inner_size` apply to the outer rect, R2-13 says the shadow setting gives a 1 px white border and no top border on Windows 10, and R4-29 enables shadow only on Windows 11. R4-06 needs a workaround for hidden undecorated size restore, while R2-05 says tao 0.37.2 fixes the same growth.
- **Saving window state.** R2-11 suggests debouncing by about 300 ms. R4-08 uses 1000 ms and writes on `CloseRequested`.
- **WebView2 user data folder.** R1-19 says the default is next to the exe and that Tauri's placement is unverified. R3-05 states the Tauri default is `%LOCALAPPDATA%\<identifier>\EBWebView`.
- **Many chunks against few.** R1-27 relies on code splitting and lazy viewer chunks. R2-25 says many chunks can push the CSP header past 16 KiB on macOS and blank the app.
- **Surviving a killed Android renderer.** R1-28 says handle `WebViewClient.onRenderProcessGone`. R2-35 says wry does not implement it and apps cannot opt in.
- **Old WebView support in the build.** R1 (discarded) says adding `@vitejs/plugin-legacy` brings no gain and R1-25 keeps `chrome89`. R4-20 uses `@vitejs/plugin-legacy` for modern polyfills only. R3-15 says do not adopt the sideload plugin that R4-21 uses.
- **Rust profile.** R1-23 and R3-21 follow Tauri's `opt-level = "s"` and `panic = "abort"`. R1-24 and its discarded list say `z`, thin LTO and similar are a coin toss. R4-34 suggests trying `z`, and notes Jan and Spacedrive keep `panic = "unwind"`. R4-33 says LTO makes no difference to `.text` once `codegen-units = 1`.
- **Memoisation.** R1 (discarded) says memoising everything is not advised and points to the React Compiler (R1-39). R3-13 got its win partly from `React.memo` rows plus list virtualisation.
