# 13 · Full audit and redesign (v0.10)

This document records what the full audit found and what replaced it.
Docs 01–12 remain the product intent; where they describe mechanics
(themes, onboarding screens, the string-patched Android activity),
this document and the code are authoritative.

## Audit findings

### Native and backend

| Finding | Impact | Resolution |
|---|---|---|
| The Kotlin "Open with" layer was injected into the generated activity by a 768-line string-patching script, with "upgrade" logic for previously patched files | CI regenerates the Android project on every run, so the upgrade paths were dead code; any template drift broke builds in opaque ways | `src-tauri/android/MainActivity.kt` is real Kotlin source copied over the generated file by `scripts/install-android.mjs`, which also validates it in CI |
| One `pendingPath` slot for incoming files | A second share while the first was being delivered overwrote it | A delivery queue; `SEND_MULTIPLE` supported |
| Imports deduplicated by name + size | Two different files with the same name and size could open the wrong content | Copies live at `imports/<sha256>/<name>`, deduplicated by content |
| The 250 MB / 30-day cache cap in the architecture doc was never implemented | Unbounded storage growth | `imports_prune` removes orphans and evicts the oldest copies over the cap; affected recents are marked unavailable |
| Store keys were silently sanitised (`a.b` and `ab` shared a file) | Silent key collisions | Keys are validated and rejected |
| Stringly-typed errors, one flat `lib.rs`, blocking I/O on the async runtime | Hard to test and branch on | `error.rs` (typed `{kind, message}`), `store.rs`, `imports.rs`, `spawn_blocking`, 9 unit tests |
| Picked content URIs used temporary grants | Recents failed after a restart | The picker bridge takes a persistable grant when the provider allows it |

### Frontend

| Finding | Resolution |
|---|---|
| A 2,800-line custom PDF engine (gesture state machine, fling physics, raster cache) | pdf.js's own `PDFViewer`, `PDFLinkService` and `PDFFindController` (the Firefox reader engine); pinch zoom uses `updateScale({scaleFactor, origin, drawingDelay})` exactly like pdf.js's reference app |
| PowerPoint, `.doc`, `.xls`, `.ppt`, ODF and RTF all ended in a dialog | PPTX renderer, SheetJS for `.xls`/`.ods`, text extraction for `.doc`/`.ppt`/`.odt`/`.odp`/`.rtf` |
| 480 ms artificial splash and a multi-screen onboarding before the first file | Removed; Home's empty state explains the app, and "Open with" goes straight to the file |
| Five themes, nested settings subpages, "Clear recents" implemented as a toggle, About showed a hard-coded `0.9.0` | Auto/Light/Dark/Black, one settings page, real buttons, version from `package.json` |
| Runtime CSS-in-JS (styled-components + Babel plugin) on every screen | CSS Modules and design tokens in CSS variables |
| All viewer engines in one chunk | One lazy chunk per engine; Home loads ~64 KB of gzipped JS |
| No real legacy/ODF fixtures (8-byte stubs) | Real files generated by `scripts/make-office-fixtures.py` |

## Research notes

- PDF: pdf.js 4.10's `web/pdf_viewer.mjs` component exposes the same viewer the
  Firefox reader uses; its `updateScale` accepts an `origin` and a
  `drawingDelay`, which gives CSS-preview pinch zoom with a delayed
  crisp redraw.
- PPTX: the maintained open-source renderers (`@aiden0z/pptx-renderer`,
  `pptx-preview`) depend on echarts (~1 MB), which breaks the size budget.
  Paperwren's renderer follows the same inheritance pipeline those projects
  document (master → layout → slide for backgrounds, decorative shapes and
  placeholder geometry; master text styles → placeholder list styles →
  paragraph → run for text) on top of `fflate`, which was already a dependency.
- Legacy Word text follows [MS-DOC] (FIB → CLX piece table, compressed
  8-bit and UTF-16 pieces, field codes hidden); legacy PowerPoint text
  follows [MS-PPT] record traversal (slide containers first,
  `SlideListWithText` as the fallback). SheetJS's bundled CFB reader opens the
  compound files, so no new dependency was needed.
- Search highlights in DOM-rendered documents use the CSS Custom Highlight
  API, so the document DOM is never mutated.

## Test coverage

- Unit (vitest): format sniffing for every fixture, extraction for
  `.doc`/`.ppt`/`.odt`/`.odp`/`.rtf`, the PPTX parser (inheritance,
  fills, runs, bullets, tables, notes), recents and settings rules
  including migration from the previous version's storage.
- Rust: store atomicity and key validation, import path safety,
  pruning and eviction.
- Browser (Playwright, production build): every format opens, recents
  persist across reloads, search/filter/pin/remove, PDF paging, zoom and
  find, Word find, slides, theme persistence, Back ordering, and error
  states (unsupported, damaged).
